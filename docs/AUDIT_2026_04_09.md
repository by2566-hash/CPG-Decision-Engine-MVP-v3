## Interface Status

### constraints.py
- `check_all(candidate: dict, signals: dict, policy: dict) -> PolicyDecision` ✅ confirmed
- `compute_risk_score(candidate, signals, policy) -> float` — delegates to `check_all().risk_penalty`
- `_VIOLATION_WEIGHTS` dict (module-level):
  ```python
  {
      "margin_floor":        3.0,   # financial safety — highest penalty
      "inventory_gate":      2.5,   # operational safety
      "incrementality":      2.0,   # ROI validity
      "discount_last_resort": 1.5,  # process constraint
      "cold_prospect_gate":  1.5,   # targeting constraint
  }
  # Unlisted violation type defaults to 1.0
  ```
- risk_penalty = weighted sum of violations (not raw count) ✅

### scoring.py
- **No direct `ConstraintEngine` import** ✅ confirmed
- Imports: `from ..contracts import MerchantStateVector, PolicyDecision`
- Consumption pattern (lines 120–137):
  1. Reads `a.get("constraints_result")` from candidate
  2. If `isinstance(raw_cr, PolicyDecision)` → use directly
  3. If `isinstance(raw_cr, tuple)` → legacy bridge: constructs `PolicyDecision` from `(bool, list[str])`
  4. Else → `PolicyDecision(eligible=True)` default
  5. Passes `(constraints_result.eligible, constraints_result.violations)` tuple to `DecisionVerifier.verify()` (DecisionVerifier still expects legacy tuple)
  6. Uses `constraints_result.risk_penalty` directly in scoring formula — no duplicate `check_all()` call ✅

### pipeline.py
- `_generate_candidates()` (lines 413–419):
  ```python
  policy_decision = _constraint_engine.check_all(
      candidate=candidate, signals=signals, policy=policy,
  )
  candidate["constraints_result"] = policy_decision  # stores PolicyDecision object
  ```
  ✅ `constraints_result` is a `PolicyDecision`, not a tuple

## V3.5 Decisions in CLAUDE.md

1. **Layer renaming**: L0 → Signal Plane, L1 → Merchant State Plane, L5 → Learning Fabric
2. **MSM constraint**: "MSM is decision routing state only — not complete feature representation"
3. **Fast Plane constraint**: "Only serves PublishedCard and execution commands, never raw candidates or unverified decisions"
4. **L3 → Decision Core**: 5 sub-modules in strict order (L3.1 Candidate Proposal → L3.2 Correlation → L3.3 Policy Evaluation → L3.4 Scoring → L3.5 Verification)
5. **PolicyDecision unified interface**: replaces `(bool, list[str])` tuple + separate `float` from `compute_risk_score()`; `risk_penalty` is weighted sum not count
6. **DecisionState vs DecisionFeatureVector split**: MSM = routing (discrete states), FeatureVector = model input (continuous values)
7. **8 core data objects**: `StateSnapshot`, `RawCandidate`, `CorrelatedCandidate`, `PolicyDecision`, `ScoredCandidate`, `VerifiedDecision`, `DecisionCard`, `PublishedCard` — plain dicts forbidden for these
8. **L5 four-log split** (conceptual, not yet physical): Decision Log / Execution Log / Outcome Log / Feature History
9. **Not building**: OPA integration, PublishedCard as separate type, entity graph in Phase 1
10. **Phase 2 deferred**: L4 physical reorganization (LLM Renderer still in layer2_decision/), CorrelatedCandidate Pydantic type, Feature History table split

## Current Phase Roadmap (from README.md — verbatim)

### Phase 1 — Active Now
- Shadow mode: all decisions logged with `was_executed=False`, no external execution
- Deterministic LLM rendering (template-based, no API calls)
- MSM health computation across 4 dimensions with configurable thresholds
- Full verification chain (DecisionVerifier → Renderer → 5-Gate)
- ImpactCalculator using industry benchmark priors (confidence ≤ 30%)
- RollbackRegistry with 48h TTL for all write actions
- MerchantApprovalGate enforcing human confirmation
- Weekly planning with conflict detection

### Phase 2 — Activation (First Paying Customers + Knowledge Layer)

Two parallel tracks that must converge before Phase 3.

**Track A · Commercial Activation** *(blocks first paying customer)*
- Shopline data connector: orders, inventory, catalog → real MSM signal computation
- LLM API integration: replace DeterministicRenderer with real merchant copy
- Web Dashboard + one-click approval workflow (was_executed transitions from False → True)
- Shopline write API: execute approved actions (retention discounts, reminder campaigns)
- ImpactCalculator upgraded: as WSM outcomes accumulate, confidence scales above 30% → RECOMMENDATION cards auto-promoted
- Multi-merchant BenchmarkEngine: peer comparison once 2+ merchants in production
- Performance billing activation: 10% of outcome_delta (requires 30-day reward cycle)

**Track B · KG Knowledge Layer** *(partner-dependent, parallel to Track A)*
- Partner Playbook YAML translation: domain expert content → typed graph facts in `playbook_registry`
- L3 physical sub-module split: `pipeline.py` decomposed into 5 discrete files matching L3.1–L3.5
- Multi-merchant test fixture: deterministic multi-brand signal sets for regression testing
- `DecisionFeatureVector` wired into scoring: replaces raw `signals` dict as bandit context contract

*Track B has no hard dependency on Track A — it advances as partner content is delivered.*

### Phase 3 (6–12 months) — Learning at Scale

Prerequisites: Track A complete (real execution data), 6+ months of action_log with outcomes.

**Signal Completeness**: Meta Ads + GA4 connectors, DecisionFeatureVector fully populated
**Learning Fabric**: WSM table split (4 tables), offline evaluation, LinUCB bandit activation, CUSUM drift detector
**KG Completion**: Document compiler, evidence graph, CorrelatedCandidate typed
**Scaling**: Shopline ecosystem embed, holdout-based billing validation

These TODOs predate `DecisionFeatureVector`. They should be updated to reference `DecisionFeatureVector` explicitly so Phase 3 engineers have the correct contract name.
